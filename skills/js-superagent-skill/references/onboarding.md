# 开始使用与交接

用于首次接入、安装或部署完成、空任务列表，以及用户询问“接下来做什么”。让用户知道本项目能做什么、在哪里交代任务、在哪里查看结果，并在已有授权范围内带着完成第一项有价值的工作。已有任务的普通状态查询，给出与当前状态相关的简短下一步即可，不重复整套新手介绍。

## 先说明技能能帮助用户接入和管理什么

首次安装后的引导先用简短说明建立整体认识，再结合实际状态推荐行动；不要直接跳到创建业务任务。说明本技能指导当前 Coding Agent 检查环境、安装兼容依赖、配置执行器、部署后台、接入飞书、设计和启用长期任务，以及升级、查看状态和恢复故障。技能文件安装完成只表示这些操作指引可用，实际执行由配置好的运行组件承担。

用业务语言解释相关部署阶段，并标出本项目已完成、未完成或未确认的部分。以下是能力地图，不是要求每个项目依次安装全部组件的清单：

| 阶段 | 用户获得什么 | 需要说明的条件 |
|---|---|---|
| 安装技能 | 在当前项目对话中请求接入、部署和维护帮助 | 不会自动启动后台或任务 |
| 配置执行能力 | 调用执行器完成具体工作 | 所需模型、工具、账号和材料权限按目标核验；依赖安装不等于执行可用 |
| 部署后台 | 当前聊天结束后仍可处理已配置的工作 | 需要机器持续可用、执行器和服务正常；休眠、关机或停服会影响运行 |
| 接入飞书 | 按实际配置交代工作、接收通知或进行人工审核 | 接单、通知、审核分别确认；不把一种能力接通说成全部可用 |
| 配置长期任务 | 定义持续做什么、执行节奏、成果位置、人工决定和停止条件 | 后台运行不代表已有任务；任务草稿不代表已启用 |
| 验证并启用 | 在授权范围内核对执行、审核和成果保存，再按计划持续工作 | 交代实际验证范围，首次成功不等于持续运行已经验证 |

按用户目标推荐所需接入范围：

- 先了解价值：检查项目并设计第一项工作的草稿，可暂不部署后台。
- 先完成一次工作：配置该工作所需的执行能力，通过支持的一次性路径验证成果，不强制建立长期计划。
- 希望聊天结束后持续推进：部署所需后台，配置长期任务及周期运行，并验证相关链路。
- 希望在飞书协作：补齐实际需要的接单、通知或审核能力；本地无审核任务不必为此接入飞书。
- 已有部署：沿用现有环境、任务和历史，只检查、补齐或升级本次目标需要的部分。

给出当前项目的具体判断：“已完成什么 → 目标还需要什么 → 推荐接下来做什么 → 完成后能获得什么”。已有目标和授权时直接推进对应路径，不要求用户重新选择部署套餐。操作细节分别转到 [安装与配置](setup.md)、[长期任务目录与后台](longrun-service.md)、[飞书接入](feishu.md)和[任务设计](tasks.md)。

必要时给出在当前项目对话可直接发送的部署维护指令，例如“检查这个项目的执行能力，列出还缺的接入条件”“按现有任务配置部署后台并检查健康状态”“检查现有飞书接单和审核是否可用”“升级项目后台，保留现有任务和历史”。选择最贴合当前缺口的一句，说明需用户完成的账号操作；不要默认要求用户自行安装软件、填写内部配置或学习组件命令。

## 先沿用用户目标，再判断当前状态

用户已经给出目标并授权设计、创建或运行时，继续完成授权范围内的工作；不要用推荐菜单、复述安装指令或再次请求同一授权替代执行。仅在目标尚未确定、工作已完成或确有阻塞时交接下一步。建议本身不创建或启用任务，也不发送测试消息。

从本项目 README、规则、相关资料和已有任务中识别适合长期维护的工作；只读取本次接入所需内容，不扫描其他项目。优先使用当前操作已经取得的证据，必要时按项目真实入口只读检查：

- 技能文件与依赖是否安装：`inspect.mjs` 只能证明安装事实。
- 执行器、服务及所需渠道是否就绪：用实际健康/能力检查，不因依赖齐全、CLI 登录或配置文件存在就声称可运行。
- 是否已有任务及其当前状态：读取已有列表、定义和状态。未部署或读取失败应标为“未确认”，不能解释成“零任务”并重复创建。

部署后的引导还应核对[协调者知识](knowledge.md)已接入；后台只知道工单不代表了解业务项目。

复制技能文件不会自动执行引导。通过对话安装时，安装指令应明确要求加载安装后的技能并完成这里的只读引导；手动复制后的用户可说“使用 js-superagent-skill 检查本项目，推荐下一步”。不为此增加安装钩子、后台进程或状态台账。

## 根据状态选择下一步

| 实际情况 | 用户需要知道什么 | 优先下一步 |
|---|---|---|
| 只有技能，或依赖已装但运行能力未核验 | 已完成的安装范围，以及尚未确认的执行能力 | 根据项目推荐维护目标；给出设计草稿或检查接入的具体说法，不能宣称后台已运行 |
| 后台已验证就绪，且确认没有任务 | 环境已就绪，目前没有长期任务；不会因为安装而自行开始工作 | 推荐第一项贴合项目的任务，说明输入、单轮成果与所需能力，提供创建草稿的下一句 |
| 已有 draft | 沿用该任务名称和定义，指出当前计划和真正缺少的条件 | 验证现有草稿，或在用户已有授权内接着启用和验证，不能重新建同目标任务 |
| 已有 enabled、paused、disabled 或待审核任务 | 当前状态、最近成果/等待原因、实际到期（可确认时） | 针对原任务给出查看成果、处理原待审事项、调整或恢复的说法；已启用不等于已验证持续运行，暂停与停用保持其真实含义 |
| 账号、权限或配置阻塞 | 哪一步被阻塞、已完成什么、解决后从哪里继续 | 给出具体处理入口和恢复动作；仍可设计时说明可以先完成的设计，不要求用户发送凭据 |
| 项目资料不足或状态读取失败 | 已知事实与缺少的关键信息 | 提出一个聚焦问题，或给出明确标为假设的轻量方向；不编造任务、路径、成果或后台健康 |

状态可以并存。例如服务正常但飞书未连接时，分别说明；本地无审核报告并不必然需要飞书。已完成本次目标后，无需为了展示所有分支检查无关账号。

## 给出贴合项目的建议

通常推荐一个最值得先做的行动；只有存在实质不同的选择时再给一两个替代方向。说明推荐依据、会维护什么、使用哪些已有输入、每次留下什么成果，以及还需接入的能力。任务能力映射见 [任务设计与交付](tasks.md)。

有本地资料时可从资料变化报告或待审建议开始；项目需要联网采集、源码修改或其他专门执行时，说明所需适配，不能因为目标适合长期维护就宣称内置类型已经支持。输入、频率和审核方式是建议，不自动视为用户决定。不要把每个项目都套成“每周报告”。

收尾以业务语言简短交代：当前做到哪一步、推荐行动及预期成果、用户可直接发送的一句具体指令。必要时补充替代方向或现有任务的查看/暂停方式。技术诊断按需提供，不能只罗列安装包、命令和文件路径。可复制的说法应包含本项目已确认的任务或输入；信息不足时不伪造具体名称。

例如，虚构的“团队手册”项目已有本地更新记录，后台和执行器已确认就绪、列表确认为空时：

> 项目后台已就绪，目前还没有长期任务。根据手册更新记录，建议先维护一份资料变化摘要：定期整理新增内容和待跟进事项，将报告留在项目里。
>
> 你可以直接说：“根据项目里的手册更新记录，设计资料变化报告并创建草稿，先不启用。”

只有技能安装完成时，应说明运行环境尚未核验，并把建议落到检查接入或设计，而不是套用上面的“后台已就绪”。已有任务时，下一句应指向原任务，例如“查看手册报告的最近成果和下一次运行时间”。


## 把真实入口交给用户

部署交付应把以下内容说清楚，使用本项目已确认的名称、链接或路径。不要只说“去飞书找机器人”或列出内部组件名；未核验的入口明确标为未确认，并提供当前可用的替代入口。

- **能做什么**：结合项目现有资料和已接通能力，推荐一项能立即起步的实际工作，说明输入和成果。额外需要搜索、业务适配或权限的能力单独说明，不能当作已经可用。
- **在哪里交代任务**：说明当前 Coding Agent 项目对话可以负责设计、配置和维护。飞书只有在真实接单入口、目标群、机器人和用户准入已确认后，才给出具体群/会话入口及所需的真实 @ 操作；仅接通审核卡片不代表可以在飞书创建任务，也不代表一句自然语言能创建长期计划。按当前版本与项目路由区分一次性工单和长期任务配置。未接通飞书接单时，直接引导在当前项目对话交代目标。
- **在哪里看结果**：给出实际成果文件/目录或链接，以及已配置的通知位置。区分接单回执、执行进度、待审核和最终成果；工单完成不等于长期任务成果已核验采纳。尚未运行时说清预期保存位置，不能把它描述成已有成果。
- **如何继续互动**：围绕推荐任务给出简短可用的说法，覆盖交代工作、查看成果和提出修改。每句话标明发送位置；查看、调整频率或暂停的请求应交给已验证支持该动作的入口。已有飞书工单的补充沿原话题和订阅关系处理，不让用户另开重复请求。

入口信息从本次部署配置、实际回执和已有项目材料取得；不为制作引导额外发送消息或扩大群准入。普通维护时只补充变化的入口，不重复整份介绍。

## 带着完成第一次使用

优先沿用用户已有目标或已有任务；没有目标时，先基于项目材料拟出一项范围小、结果可检查的任务草稿，包括输入、要做的事、成果位置和验收标准。首次体验可以是一项一次性工作或长期任务的一轮，不必为了展示能力新建长期计划。频率、审核与停止条件按实际长期目标设计。

已授权执行时，连续完成能力核对、任务配置、首轮执行和成果检查，直到能够带用户看到实际结果。不要在准备好之后仅回复“你可以说开始”。用户仅授权安装或部署时，仍先完成项目化建议和可审阅草稿，再给出在具体入口可直接发送的执行指令；不能把部署授权扩成真实运行、发消息或启用周期任务。

首次运行应跟进原任务到成果或确切交接点：

- 成功时打开并核对真实产物，简要说明完成了什么、成果入口和一项后续修改的说法。长期任务另说明是否已启用、实际下一次运行时间（可确认时）及暂停入口；一次运行成功不证明周期运行已验证。
- 等待人工审核时，指出原卡片或待审入口、需要用户决定什么，以及提交后原任务将如何继续；不代用户作决定。
- 失败或阻塞时，说明已完成部分、具体阻塞和原任务恢复入口；可在授权内修复的继续修复，不另建任务掩盖失败。
- 需要用户在飞书亲自发起或完成账号操作时，提供准确位置、要做的动作和预期回执；恢复后核对原请求，不要求用户重复发送。

首次交付以实际成果或当前交接点为主，附上够用的日常操作说明。验收标准是用户能够回答“这个技能能帮我接入和管理什么、项目部署到哪一步、我可以让它做什么、去哪里说、去哪里看、下一步怎么用”，而不是安装清单全部打勾。

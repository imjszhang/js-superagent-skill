# 开始使用与交接

用于首次接入、安装或部署完成、空任务列表，以及用户询问“接下来做什么”。让用户知道目前能做什么，怎样开始第一项有价值的工作。已有任务的普通状态查询，给出与当前状态相关的简短下一步即可，不重复整套新手介绍。

## 先沿用用户目标，再判断当前状态

用户已经给出目标并授权设计、创建或运行时，继续完成授权范围内的工作；不要用推荐菜单、复述安装指令或再次请求同一授权替代执行。仅在目标尚未确定、工作已完成或确有阻塞时交接下一步。建议本身不创建或启用任务，也不发送测试消息。

从本项目 README、规则、相关资料和已有任务中识别适合长期维护的工作；只读取本次接入所需内容，不扫描其他项目。优先使用当前操作已经取得的证据，必要时按项目真实入口只读检查：

- 技能文件与依赖是否安装：`inspect.mjs` 只能证明安装事实。
- 执行器、服务及所需渠道是否就绪：用实际健康/能力检查，不因依赖齐全、CLI 登录或配置文件存在就声称可运行。
- 是否已有任务及其当前状态：读取已有列表、定义和状态。未部署或读取失败应标为“未确认”，不能解释成“零任务”并重复创建。

部署后的引导还应核对[协调者知识](knowledge.md)已接入；后台只知道工单不代表了解业务项目。

复制技能文件不会自动执行引导。通过对话安装时，安装指令应明确要求加载安装后的技能并完成这里的只读引导；手动复制后的用户可说“使用 js-superagent-skill 检查本项目，推荐下一步”。不为此增加安装钩子、后台进程或状态台账。

## 根据状态选择下一步

| 实际情况 | 用户需要知道什么 | 优先下一步 |
|---|---|---|
| 只有技能，或依赖已装但运行能力未核验 | 已完成的安装范围，以及尚未确认的执行能力 | 根据项目推荐维护目标；给出设计草稿或检查接入的具体说法，不能宣称后台已运行 |
| 后台已验证就绪，且确认没有任务 | 环境已就绪，目前没有长期任务；不会因为安装而自行开始工作 | 推荐第一项贴合项目的任务，说明输入、单轮成果与所需能力，提供创建草稿的下一句 |
| 已有 draft | 沿用该任务名称和定义，指出当前计划和真正缺少的条件 | 验证现有草稿，或在用户已有授权内接着启用和验证，不能重新建同目标任务 |
| 已有 enabled、paused、disabled 或待审核任务 | 当前状态、最近成果/等待原因、实际到期（可确认时） | 针对原任务给出查看成果、处理原待审事项、调整或恢复的说法；已启用不等于已验证持续运行，暂停与停用保持其真实含义 |
| 账号、权限或配置阻塞 | 哪一步被阻塞、已完成什么、解决后从哪里继续 | 给出具体处理入口和恢复动作；仍可设计时说明可以先完成的设计，不要求用户发送凭据 |
| 项目资料不足或状态读取失败 | 已知事实与缺少的关键信息 | 提出一个聚焦问题，或给出明确标为假设的轻量方向；不编造任务、路径、成果或后台健康 |

状态可以并存。例如服务正常但飞书未连接时，分别说明；本地无审核报告并不必然需要飞书。已完成本次目标后，无需为了展示所有分支检查无关账号。

## 给出贴合项目的建议

通常推荐一个最值得先做的行动；只有存在实质不同的选择时再给一两个替代方向。说明推荐依据、会维护什么、使用哪些已有输入、每次留下什么成果，以及还需接入的能力。任务能力映射见 [任务设计与交付](tasks.md)。

有本地资料时可从资料变化报告或待审建议开始；项目需要联网采集、源码修改或其他专门执行时，说明所需适配，不能因为目标适合长期维护就宣称内置类型已经支持。输入、频率和审核方式是建议，不自动视为用户决定。不要把每个项目都套成“每周报告”。

收尾以业务语言简短交代：当前做到哪一步、推荐行动及预期成果、用户可直接发送的一句具体指令。必要时补充替代方向或现有任务的查看/暂停方式。技术诊断按需提供，不能只罗列安装包、命令和文件路径。可复制的说法应包含本项目已确认的任务或输入；信息不足时不伪造具体名称。

例如，虚构的“团队手册”项目已有本地更新记录，后台和执行器已确认就绪、列表确认为空时：

> 项目后台已就绪，目前还没有长期任务。根据手册更新记录，建议先维护一份资料变化摘要：定期整理新增内容和待跟进事项，将报告留在项目里。
>
> 你可以直接说：“根据项目里的手册更新记录，设计资料变化报告并创建草稿，先不启用。”

只有技能安装完成时，应说明运行环境尚未核验，并把建议落到检查接入或设计，而不是套用上面的“后台已就绪”。已有任务时，下一句应指向原任务，例如“查看手册报告的最近成果和下一次运行时间”。

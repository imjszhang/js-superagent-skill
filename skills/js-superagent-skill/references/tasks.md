# 长期任务设计与交付

## 1. 从长期目标形成任务约定

先读取项目规则、已有任务、相关成果和历史决定。对重复请求复用同一任务；对新目标分配独立 ID 与成果目录，不能覆盖其他任务。仅对不能从上下文确定且影响执行的事项提问；可逆的普通选择采用明确假设，不把所有字段变成一次问卷。

用 [任务说明模板](../assets/task-brief.md) 写入项目选定的任务说明，至少落实：

- **维护目标与单轮成果**：长期要维护什么，每次实际交付什么；分别定义合格成果与何时停止长期维护。
- **输入与积累**：允许读取的文件/来源，资料如何更新，上轮记忆与历史决定如何使用。记忆是有来源的记录，不是无限理解全仓库或自动学习偏好。
- **输出与写入者**：允许写入的实例目录，正式成果如何核验后采纳；共享文件先有保留其他写者的合并规则。
- **节奏与限制**：固定间隔还是结算后等待，时区、首次到期、运行次数、执行/排队期限；额度不是精确 token/金额预算。
- **人工参与**：是否逐项审核、审核者/渠道、超时后如何保留、哪些决定可重审；自动报告无需强加逐项审核。
- **异常与结束**：无变化怎样记录，失败/冲突怎样处理，谁能暂停和停用；是否取消在途工单另行明确。

## 2. 把设计映射到真实能力

| 任务 | 入口 | 必须说明的边界 |
|---|---|---|
| 一次性成果 | superagent 普通工单 | 不强行引入长期回合 |
| 本地资料定期报告 | `change-report@1` | 不逐项审核，不联网 |
| 本地资料候选建议 | `review-items@1` | 结构化采用/拒绝/稍后及理由，支持显式重审 |
| 搜索、外部采集、制作或特殊业务结构 | 项目适配器/可信子任务 | 先接入真实工具、验证与成果写入，不把 prompt 当作已有能力 |

使用 `types/design` 和已安装包定义核对可用字段。当前内置任务 completion 只有 `until-disabled`：任务持续到停用；目标达成、截止日期自动结束等需求需要宿主支持，不能编造字段或声称已实现。通用业务结算/失败外发通知目前未实现，不能承诺每次入库自动发消息；Worker 完成通知不是业务采纳通知。

内置 `local-worker@1` 无受管子任务，相关限额为 0。`fixed-interval` 表示从带时区 anchor 起每隔指定小时，不等于任意 cron/每月规则；`after-settlement` 则从结算后等待。内置执行时长上限当前为 60 分钟。用户要求超出能力时保留需求并明确需要适配，不能静默缩小目标。

## 3. 创建草稿并验证计划

已有宿主 wrapper 注册业务路由时，所有 task/tick/watch 操作继续使用该入口。以下是通用项目的例子，先核对所用版本 help；任务 ID、路径与频率由项目设计决定。

```sh
./node_modules/.bin/js-longrun --project <root> list
./node_modules/.bin/js-longrun --project <root> design weekly-report --type change-report@1
./node_modules/.bin/js-longrun --project <root> create weekly-report --type change-report@1 --goal '总结提供的本地资料变化'
./node_modules/.bin/js-longrun --project <root> validate weekly-report
./node_modules/.bin/js-longrun --project <root> plan weekly-report
```

create 生成 draft；编辑 task.json 和 task.md 后再 validate/plan，检查实际输入、输出边界与依赖。重复 ID 先读现有任务，不覆盖。可参考经过离线测试的 [报告定义](../assets/report-weekly.task.json)和 [审核定义](../assets/review-weekly.task.json)：它们是示例，需替换 ID、时区、资料路径与规则；不能复制示例就启用生产。内置输入必须是项目内真实 UTF-8 普通文件。

`trial --result <fixture.json>` 是隔离夹具检查，不调用模型或发卡，不能当成真实运行。新增任务可共享项目已有服务与 watcher，无需按任务重复部署一套后台。

## 4. 启用与首次运行

只完成用户要求的阶段。设计/创建请求到草稿和计划为止；已明确要求部署并运行，则在能力与账号具备后继续启用和验证，不重复请求同一授权。enable 的 reason 记录真实授权依据，不能填入虚构同意。

`enable` 记录运行授权，不立即派工；`round` 检查启用、到期、额度及活跃回合。`watch` 只收集；`tick` 默认补收/检查，显式 `LONGRUN_OPEN_ROUNDS=1` 才会开符合条件的回合。配置后台后核对生产入口只指向本项目，一个项目 watcher 与一个兜底定时入口覆盖已注册任务。

首次验证按任务方式执行：无审核任务核对结果和记忆；审核任务核对发卡、真实用户答案、原 Worker 续作及结果采纳。验证层级见 [运行维护](operations.md)。测试使用隔离任务与虚构材料，不能为测试绕过生产门控、代答真实候选或改变用户决定。

## 5. 把运行交回项目

在项目已有运行说明/任务记录中保留：任务 ID 与定义位置、采用的组件版本与入口、执行/审核责任、运行间隔与限制、当前控制状态、实际下次到期、后台与兜底归属、成果/历史位置，以及查看、暂停、恢复和故障检查方法。不要另建一份复制数据库状态的台账；状态以系统实时读取为准。

明确已验证到哪一层及尚需完成的操作。卡片送达、答案保存、Worker 完成和业务结算分别报告。定时任务未部署或账号未就绪时，不能把 enabled 说成已在持续工作。

后续调整、重新审核、暂停/恢复与退役按 [运行维护](operations.md)执行。每轮使用独立身份和冻结定义，正式成果经核验后采纳，历史不因新设计被覆盖。

首次任务交付或用户不清楚如何继续时，按 [开始使用与交接](onboarding.md)把上述记录转成简短的使用说明和针对原任务的下一句。设计完成交接到验证/启用；已授权继续的步骤直接完成，不以“是否继续”重复征求同一授权。

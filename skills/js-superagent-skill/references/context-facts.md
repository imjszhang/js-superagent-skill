# 协调者的运行事实

排查“漏看在途工作”“把失败或取消归因给人”或“没有活跃工单就说没有长期任务”时，先核对协调者这一次实际获得的事实。项目背景、当前执行和业务结算分别有自己的来源；增加事实不改变协调者、Worker 和领域服务的职责。

## 三类事实与各自来源

| 事实 | 权威来源与接入方式 | 需要分别说明的内容 |
|---|---|---|
| 项目长期任务概览 | longrun 根据任务定义和当前状态生成 project 范围宿主事实 | 已配置任务、控制状态、回合数、当前回合及其阶段、下一次到期和来源是否可读；没有活跃工单时仍有概览 |
| 工单的业务关系与历史 | longrun 根据原回合的 outcome、binding 和结算记录生成 ticket 范围宿主事实 | task/run/ticket/domain/assignment 身份、round/review 类型、已保存终态、结算是否 applied、摘要和错误数量；宿主业务适配器可补充自己能证明的关系与结果 |
| 工单当前执行 | superagent 自己的持久工单、Assignment、执行观察和最近报告 | 当前状态、execution run/assignment、执行观察时间、最近报告时间与摘要、业务关联和已记录取消来源；更多输入交接细节仍按原公开查询能力检查 |

通用任务概览当前不内嵌“最近一轮结果”，也不计算所有不能继续的原因；详细结果从已发布的工单历史核对，调度门槛仍查原任务状态入口。通用回合事实在终态 outcome 存在后生成，不是每个中间业务阶段的台账；原轮与重审条目的对应关系只有适配器明确提供且有依据时才可陈述，不能从 review 类型自行推断。

每条宿主事实应能定位生产者、稳定 key、源版本和 `observedAt`。核对报告自身时间与观察时间；已有执行仍在运行时，旧报告不能代替当前进度。缺失、读取失败或时间滞后应明确呈现；只有成功读取且确实为空，才称“没有任务”或“没有报告”。

取消属于什么业务结果、由哪个入口触发、是否能确认操作者，是不同事实。`source`、操作原因与证据引用可以解释来源；仅有 cancelled 或“人工停止”分类不能证明是用户本人要求取消。旧记录缺少归因时保持 unknown，不按名称、模型文案或后来对话补写历史。

## 组件边界

longrun 拥有任务与结算事实，通过 superagent 的通用宿主事实接口发布可重建的只读投影。superagent 负责按当前会话及材料权限把允许的事实交给协调者，并补充自己掌握的执行信息。协调者在完整信息下理解请求、协调工作；Worker 负责执行与技术步骤，领域服务继续校验合法状态转换。

这层投影不是新的业务状态库：卡片已提交、原 Worker 已完成、longrun 已结算、协调者视图已同步是四个不同事实。结算成功但同步失败时，保留业务成功并报告同步诊断，不重新结算、不重复采用成果。已取消但尚未收集时也应保留“待结算”的区别。

工单创建时携带稳定业务关联；历史回合、当前回合和重审不能因标题相同合并。暂停、停用或定义变更仍按原有授权与生命周期处理：事实接口不改成另一套取消规则，也不增加新的确认步骤。

`knowledge/` 保存项目目标、术语、规则摘要与资料入口；当前回合和进度通过运行事实接入，不用定时改写 Markdown 镜像。js-agent-runtime 仍是可选执行适配，lark-cli 仍用于接入与诊断。Skill 不常驻同步，也不建立另一套 watcher、消息订阅或定时器。

## 安装与能力核验

`inspect.mjs` 仅读取安装清单与允许的项目配置。其 `hostFacts` 输出列出缺失组件，并把 capability 与同步均标为 `not-observed`；包版本、导出名或源码中出现函数名不能证明运行能力。检查本身不导入运行包，不调用 `.init()`，不读取业务数据库，也不创建服务。

实际接入已经获准后，在项目已有连接的 SDK 或隔离验收环境中核对以下公开合同，并以所安装包的类型和文档为准：

- `hostFactsCapabilities()` 返回 `{version: 1}`；旧 SDK 没有该方法时明确为 unavailable，未知协议明确为 unsupported。可将已获取的结果交给 `scripts/compatibility.mjs` 的 `hostFactsCompatibility` 分类；省略参数表示尚未观察，`null` 表示已确认能力缺失。
- `publishHostFacts` / `listHostFacts` 提供 project/ticket 范围的事实发布与读取；发布使用生产者、稳定 key、源版本、观察时间与结构化 facts，ticket 事实同时核对工单及 domain/assignment 归属。重试可能沿用公共 ticket ID 但产生新 domain 或 assignment，不能把旧关联套到新执行。这个协议结果不代替 knowledge 的准确版本/schema 兼容矩阵。
- longrun 使用实际已有的 SDK 连接与业务入口发布投影，记录本次同步结果；缺能力或发布失败应可见，不静默称为已接通，也不阻断本来成功的结算。

沿用 longrun 现有启动、watcher、tick 和已连接的业务生命周期同步机会。纯本地创建/修改/暂停操作仍可离线进行，不能为“立即刷新”偷偷初始化 SDK。离线变更在下一次已有连接的同步机会反映；同时说明最后观察时间。旧 SDK 仍可使用原有任务功能，补充事实能力需要单独按版本核验。

发布的任务摘要仍受隐私与访问边界约束：项目概览只给既有受信本地操作者或已配置的私聊操作者；群聊跟进不因此获得项目总览。工单事实按原工单归属、材料读取者与输出目的地重新核验，授权撤回后不能因为摘要已缓存而继续带入协调者。不要为通过验收扩大材料授权或替换账号。

## 对话没有回复时

先检查原消息及查询回合，而不直接重发请求。受信操作者的协调查询遇到终态 failed/unsupported 时，固定回执沿原回复路径交付；会重试的故障先走既有有限重试。当前文案说明“本次协调未完成，尚未提交协调动作”，保留原请求，并提示检查原因后重试。它没有附带专门的恢复命令，也不宣称全部失败都可恢复；具体检查与恢复仍按所安装版本的事件诊断及已有操作入口核对。回执不是业务完成、人工审核或自动重试授权。

核对失败记录、出站记录和平台实际送达，保留 pending/sent/failed 等区别。升级不补发全部旧失败，也不恢复旧请求。原路由拒绝或发送结果未知时保留诊断，不转发私聊、用 lark-cli 代发或修改消息身份来绕过。

## 接入与升级验收

先记录依赖准确版本、服务入口、既有任务/回合/审核状态和当前运行意图；只更换本次授权范围内的组件。新协议通过不意味着已发布到 npm，也不意味着目标项目已经接入。

1. **安装清单**：`inspect` 不执行包代码、不新增文件或状态；支持与未观察明确分开。已有准确版本/schema 知识检查继续通过。
2. **公开能力与同步**：在隔离候选或已有连接里读取 capability，核对 longrun 的同步结果、稳定身份与源版本；重复同步不重建工单、不改业务记录。缺能力与失败均有明确诊断，失败后重试同步不重复结算。
3. **实际协调者输入**：同时有旧终态工单与当前在途工单时，两者及其归属、执行与业务阶段均可见；没有活跃工单时，仍能说明已配置长期任务与到期原因。读取失败不变成空列表，旧归因保持 unknown，旧报告不掩盖本轮执行。
4. **权限与历史**：受信操作者可见所需概览，非授权群聊看不到；材料权限撤回后工单事实不可见。重复检查及升级不改历史回合、审核决定、预算、材料绑定和来源游标。
5. **故障回执**：隔离注入最终查询失败，核对原路由、原请求保留、重复投递去重与无新执行；旧失败不因升级自动补发。模拟通道不代表真实飞书送达。
6. **完整链路**：仅在获准的隔离任务或真实测试任务核对定时触发、飞书答案持久化、原 Worker 完成、即时结算及视图更新时间。期间不手动 collect/tick 冒充自动链路；已有业务实例保留。用户还没提交卡片时，明确该环节待验收。

收尾分别报告安装、能力、同步、实际输入与业务链路证据，恢复原来运行的服务并清理测试实例；原本停止或未启用的服务与任务保持原状。

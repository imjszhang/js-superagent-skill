# 运行维护与验收

## 观察顺序

先读项目任务状态与原工单身份，再用现有 CLI/SDK 检查后台健康、工单状态、attention、答案、执行报告和结算结果。读取 status 不应启动 Worker、开轮或发送请求；`request-status` 会给 Worker 发输入，不等于只读查看。

飞书部署、升级或恢复按[飞书只读检查与补收验收](feishu.md)检查应用 bot scope、实际群/话题历史 API 和积压区间。健康快照、实时连接和历史轮询分别判断；不要调用临时 SDK `.init()` 或执行循环做诊断。`0.15.0-alpha.4` 及之前 `businessHealth()` 会刷新健康状态，读取旧版本时用已有服务心跳/持久快照；`0.15.0-alpha.5` 的健康读取使用已保存观察，时间滞后需如实报告，不替代 bot API probe 或实际补收。

要区分：未到期/额度不足；queued；running；waiting；failed/interrupted；completed；settled/invalid/conflict。通知送达不证明答案已保存，答案保存不证明 Worker 完成，Worker 完成不证明正式成果已写入。

飞书审核正常路径由已有通道维护：卡片 → 持久结构化答案 → 原 Worker → watcher → 核验/结算。兜底 tick 负责遗漏、超时、冷却到期；不要建立另一个无限轮询脚本重复收集或启动另一个事件消费者。

## 日常维护与任务调整

先列出本项目已注册任务，逐项报告任务目标、控制状态、当前回合/工单、等待原因、实际下一次到期与成果入口。一项任务配置损坏不应阻止查看其他实例；不要重建注册表来消除错误。区分正常冷却、已达限额、等待人的决定与真正故障。只读检查不触发定时器、模型、收集或通知。

确认任务列表为空，或用户询问下一步时，按 [开始使用与交接](onboarding.md)给出贴合项目的建议；列表读取失败不能当作零任务。已有任务的建议沿用原身份与真实状态，避免重复部署、重建或擅自恢复。

用户要求改频率、输入、审核标准或限额时：

1. 读取当前定义、revision、实际 nextDueAt、活跃回合及其冻结定义，保留变更前记录；根据范围决定同任务调整还是独立新任务。更换目标/类型或输出所有者通常应新建，不能把旧工单硬接到另一类型。
2. 用户只要求改后续配置时不取消在途工作。需要避免改动期间开启新回合，可暂停该任务并记录原控制状态；不要停整个项目。现有 disabled/draft 保持原状态。
3. 通过项目支持的入口修改任务说明和定义、增加 revision，保持 ID、原成果、审核证据与历史不变；当前通用 CLI 没有 update/reschedule，需编辑 task.json/task.md 后 validate/plan，不能编造命令。
4. 报告新定义作用于未来冻结回合。已运行回合仍按原快照结算；既有 nextDueAt 不因编辑频率或 pause/resume 自动重算，当前回合结算也按旧冻结定义计算下一次到期。**改成每两周，不等于下一次立即改到两周后。** 若用户要求精确重新排期，先查宿主能力；当前通用入口不支持时明确限制，不手改 state 或绕过冷却。
5. 验证后恢复本次临时暂停且原本 enabled 的任务；原来 paused/disabled 的任务不擅自启用。若验证失败，恢复已备份的定义并复核；不能安全恢复时保留明确暂停状态及待办，不悄悄遗留停机。

plan 描述下一份计划，不等于旧工单将改用该计划；报告定义变化、在途身份、实际到期与后台状态四项结果。调整时保留 task.md 与任务记忆的来源，不能把一次测试决定当成用户偏好，或重写已冻结的历史。

## 暂停、恢复、停用与立即停止

按目标项目已有入口调用；下表为当前通用 longrun 行为。

| 用户意图 | 操作与结果 |
|---|---|
| 暂停后续工作 | `pause <id> --reason <原因>`；阻止新回合，保留在途工单，已有结果仍可收集 |
| 恢复已暂停任务 | `resume <id>`；仅适用于有既有授权的 paused，不改原到期时间 |
| 结束长期维护 | `disable <id> --reason <原因>`；保留成果、历史与在途工单，不再开新回合 |
| 再次启用已停用任务 | 核对当前授权后 `enable <id> --reason <依据>`；不能用 resume 代替 |
| 立即停止正在执行的工作 | 先阻止后续回合，再核对原 ticket ID，用 superagent 取消接口停止该工单；longrun 没有 cancel 命令 |

“停止”未说明是否含在途工作时，先说明当前执行情况、区分两种效果；可先阻止新回合，再询问是否也取消当前工单。明确要求立即停止全部执行时，按已有授权完成取消，不再次询问同一问题。取消后核对执行退出和收集结果；失败或外部结果不明时报告事实，不把 paused/disabled 当成已经停止 Worker。

停用单项任务不卸载项目共享 watcher、定时器或服务。退役整个项目需核对其他任务及在途工作，只有用户明确要求时停止共享服务；保留状态与成果，不把停用理解成删除历史。暂停/停用后审核等待可能仍存在，向用户说明其归属和后续处理方式。

## 维护待审事项与再次审核

先核对当前问题、已保存答案和原决定。已有待审工单继续原入口，不能重复创建卡片来催促，也不能替用户选择。卡片提交后按“答案→Worker→结算”跟踪，分别陈述送达、回答和成果事实。

用户要求处理“稍后”时，列出可重审项并按授权选择；使用现有 rereview，保留原候选内容、来源回合与旧决定。通用入口使用 `R0001:I0001` 这样的复合身份，宿主业务 wrapper 可能不同，以实际帮助为准。重审需任务已启用、无活跃回合且类型允许；paused/disabled 时说明并在用户授权范围内恢复或启用，不能暗中绕过控制。

再次审核由明确操作触发，不默认循环催审全部“稍后”。用户要求自动提醒/到期重审时核对是否有宿主能力，不能把普通定时开轮当成支持提醒。无审核报告保持无审核；不要为统一界面增加无意义的人审卡片。

## 恢复决策

- 执行失败：先检查错误、原生会话、派工和待交付记录。可恢复的失败优先 retry 原工单；不要新建同目标工单掩盖失败。
- 已有会话绑定冲突：按 session inspect/恢复指导处理。未经明确决定不替换会话；不能通过手改持久配置绕过绑定。
- 已保存待交付：使用已有 delivery 恢复接口，避免重跑已完成的外部动作。
- completed 但未结算：检查 watcher、注册路由、输出路径、快照与答案证据。用户要求修复时可对目标任务 collect/tick，记录这是人工恢复；不能据此声称即时监听已通过验证。
- invalid/conflict：保留证据，解释核验失败。修复源问题或使用项目支持的恢复流程，不手改 outcome/settlement/status 来变成成功。
- 材料版本变化、准备冲突或输出目的地拒绝：按[材料恢复规则](materials.md)核对原观察、准备操作和约束。正常 waiting 的环境切换沿用原 Assignment，不能用失败 retry、新建工单或增大权限替代。
- 飞书历史读取失败：先用同一应用 bot 身份实际验证群与话题 API，区分缺应用权限、目标身份、网络和分页问题；检查失败游标及旧话题订阅，不把连接在线或能回复当成已恢复。修复后通过既有来源轮询补收，不能清游标、注入旧消息、反复重发 @ 或手动清告警；补收可能触发积压工作，须先核对原请求与当前授权。
- 连续同类错误：完成一次针对原因的修复与重试后若仍相同，停止无效重试并报告阻塞证据；不要循环增加权限、重复发卡或消耗模型额度。

在 js-superagent 0.14.0-alpha.3 中，操作者可通过原对话明确要求重新评估失败候选；协调者提出 `retryRequest`，宿主复核原请求身份、当前权限和状态后恢复。优先沿用原请求，已排队或已建单时只返回现状，不另建替代请求。状态询问不启动恢复，升级本身不重跑历史失败。

从 0.14.0-alpha.4 起，已建单但执行失败的工作通过 `retryTicket` 恢复原工单。先确认原生历史、工具与后台任务已结算，待交付结果和输入归属没有歧义；空报告与历史不可读分别诊断。自动报告修复受既有恢复策略与次数限制控制，不因升级开启自动恢复。通过飞书验收时，应核对恢复回执、原工单与会话身份、实际新运行及最终通知；回复“已受理”不等于恢复已经完成。

已完成工单的说明更正仅在对话中回复，不重开工单、不改写历史报告；普通状态查询不启动恢复。

从 0.15.0-alpha.6 起，宿主确认授权未变但评估上下文版本变化时，保留原候选并最多自动刷新两次；刷新期间仍是评估中，不另建请求或报已建单。次数跨停止、重启和自动重排保留。耗尽后查看原请求的结构化失败与回执，再按既有授权重评原请求；权限变化、原材料失效和过期回调不是这类自动恢复。没有新增重试选项，不修改 workRetry 或材料授权来“开启”它。旧 internal 失败不因升级自动重跑。

## 升级

读取包版本、engines、peer 和发布记录，确认新版本 registry 可用。记录依赖锁、服务配置及状态基线，采用服务支持的备份方式；不要在写入期间直接复制 SQLite 主文件当作完整备份。

停止需要重载该包的 watcher/定时入口及执行服务，在安装窗口避免新旧写者混用；只停止相关项目的受管进程。安装准确版本后恢复原入口与环境，检查依赖去重和服务健康。仅当版本需要状态迁移时，按其文档在停止状态执行 upgrade，不能因升级包就重建身份。

停服必须核对包装进程与工作子进程的实际退出。0.15.0-alpha.6 会阻断仍有残留进程或无法证明身份的重启／替换；`loaded:false` 不是完整停止证明。读取挂起可由停止取消，已发出的消息写入仍须等待既有回执处理；结果未知或执行未结束时报告停止未完成，保留原身份与诊断，不手动删 owner、不按裸 PID 强杀、不启动第二实例。新安装从未启动与旧运行记录无法核验是不同状态。

更新失败时，检查是否发生 schema 迁移再决定能否回退。恢复定时与服务是部署的一部分，不能在出错后把项目留在未说明的停机状态。

飞书升级还须执行[群消息与补收验收](feishu.md)：在线 @、断线群主消息、最近发现且未订阅话题中的首次 @、活跃及已订阅话题的非 @ 补充、原群回复和实时/历史重叠去重分别留证。先检查 bot 历史读取能力与原游标积压；沿用项目已有模式、准入和订阅关系，不新增用户开关，不借升级扩大群接收范围。

`0.15.0-alpha.5` 将飞书内部历史游标升级为 v2，即使数据库仍是 schema 15，也不能直接降级运行包并让旧版继续读取新游标；旧版可能把它当作首次接入而跳过积压。回退前保留升级后的输入与回执证据，核对升级前一致备份和恢复范围，不能只改依赖版本或手动改游标版本号。包布局兼容矩阵不代表运行状态支持降级。

`0.15.0-alpha.6` 保持 schema 15 和游标 v2，但增加持久刷新额度与停止状态；alpha.5 不理解这些状态，同样不能据“schema 未变”直接降级写入。先核对支持的备份／恢复流程和升级后输入，保留原工单、额度与发送证据。

材料合同进入 schema 15 后，旧包不能打开新状态。先升级知识 wrapper，使其识别准确的新包/状态组合，再按运行包流程迁移；不把 knowledge check/sync 当成升级命令。旧材料授权和会话输出约束不能靠删除配置或重建会话消除。原长期任务继续按冻结合同运行，材料部署不修改已冻结的输入。

升级至 0.15.0-alpha.4 时，检查已有 defaults 的读取者和实际输出目的地：旧版可能放弃未获授权的默认材料继续普通执行，新版会明确拒绝，不提供降级开关。不要通过删除 defaults 来恢复“能跑”的表象。若需要补材料授权，先检查在途绑定，按公开 revision 接口更新；保留失败候选和旧报告，升级或配置变更本身不授权重试、重放消息或改写旧绑定。具体群接入按[飞书接入检查](feishu.md)验收。

## 验证层级与收尾

- 单元/集成测试：验证代码和隔离状态事件，不等于真实飞书回调。
- 干净消费者安装与 trial：验证包边界、公开入口与离线格式，不等于模型执行。
- 真实工单：确认执行、结果路径与输出核验。
- 真实卡片：通过通道保存的答案必须显示真实来源，不能注入 SDK 答案后标称来自飞书。
- 自动结算：记录答案时间、Worker 完成时间和 watcher 结算时间；期间不手动 collect/tick。
- 定时兜底：可用隔离任务、临时调度验证，不能以模拟时钟测试冒充真实等待完整冷却期。

收尾核对既有业务状态、活动工单和审核决定；后台正常检查可能只刷新观测时间，区分元数据变化与业务变化，不在哈希不同后仍声称字节一致。清理临时定时器和观察进程、暂停测试实例，保留诊断记录。用户尚未完成测试卡片时报告待验收环节，保留有归属的观察安排，后续完成后清理。

安装/升级不自动发布 npm、创建 GitHub Release 或推送项目。明确要求发布时，先验证干净来源与包完整性，等待 registry 确认可见，再写发布记录和切换依赖；遇到账号验证只交接该步骤，复用已有授权。

## 项目知识维护

协调者不了解业务项目、只汇报工单状态时，先检查[项目知识](knowledge.md)的文件、同步差异和实际服务入口。先改 `knowledge/*.md`，再通过包装入口重启生效；不修改受管提示词副本，不把知识文本当成新授权。升级保留文档与原后台状态。
